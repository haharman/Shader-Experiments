# commit-message

コミット前の変更を要約し、このリポジトリの流儀に沿ったコミットメッセージ（件名 + 本文）を作る。

## 前提: このユーザーは GitHub Desktop を使う

GitHub Desktop は、変更ファイルのチェックボックスを Git のステージ（`git add`）として反映しない（コミットボタンを押した瞬間に初めて反映される）。そのため `git diff --cached` は通常ほぼ空になる。**ステージの有無を前提にせず、作業ツリーの変更を対象にする。**
GitHub Desktop の Changes 一覧は `git status`（.gitignore 反映済み、新規ファイル含む）と同じ内容なので、同じコマンドで同じ一覧が得られる。ただしチェックの ON/OFF は Git から読めない。

## 手順

1. **変更の一覧と内容を取得する**
   ```bash
   git status --short -uall
   git diff --cached --stat -M
   git diff HEAD --stat -M
   git diff HEAD -M -- . ':(exclude)*.meta' ':(exclude)*.unity' ':(exclude)*.asset' ':(exclude)*.mat' ':(exclude)Packages/packages-lock.json'
   ```
   - 対象の決め方（上から優先）
     1. ユーザーがパスや範囲を指定した（例:「StableFluids だけ」）→ そのパスに限定する（各コマンドの末尾に `-- <path>` を足す）。
     2. `git diff --cached` が空でなければ、ユーザーが CLI でステージ済み → ステージ済みの変更だけを対象にする（`git diff HEAD` の代わりに `git diff --cached`）。
     3. それ以外 → `git status` に出る変更すべて（= GitHub Desktop の Changes 一覧）を対象にする。
   - 新規ファイル（`??` で出るもの）は `git diff` に出ない。`git status --short -uall` の一覧で把握し、主要なもの（`.cs` `.shader` `.compute` など）は実際に開いて内容を読む。画像・`.meta` は存在だけ確認する。
   - 変更が何もなければ、その旨を伝えて止まる。勝手に `git add` はしない。
   - 除外した種類（`.meta` / シーン・アセット YAML / lock）は diff 本文を読まず、`--stat` と、必要なら該当ファイルだけ個別に `git diff HEAD -- <path>` で意図を確認する。YAML の行単位の変更を本文に書かない。
   - 巨大な diff は、先に `--stat` で全体像をつかみ、主要なソースファイル（`.cs` `.compute` `.shader` など）から読む。
   - 変更が複数の無関係な系統に分かれていそうなら、先に「注意」の分割案を提示し、どの範囲のメッセージを作るかユーザーに確認してよい（GitHub Desktop ではチェックを付けるファイルの組み合わせとして案内する）。

2. **直近の流儀を確認する**（任意だが、スキルの記述と食い違っていそうなら必ず）
   ```bash
   git log -n 8 --format='=====%h%n%B'
   ```
   下の「書式」と最近のコミットがずれていたら、最近のコミットを優先する。

3. **変更を分類して件名と本文を書く**（下記ルール）

4. **出力する**。コードブロックに入れてそのままコピーできる形で出し、`git commit -m` の実行はしない。ユーザーが「コミットして」と言った場合のみ、`git commit -F -`（ヒアドキュメント）で実行する。その際、環境から指示されたコミット末尾の attribution 行があれば本文の最後に付ける。

## 書式

過去のコミットから読み取った傾向。

```
<type>: <件名>

<導入文（任意）>

- <変更点を「何を実装/変更したか」で書く>
  - <その変更の工夫・理由・挙動（任意）>
- <変更点>
```

### 件名（1 行目）

- `type: 件名` の形式。**scope は付けない**（`feat(fluid):` は使わない）。type の後は半角コロン + 半角スペース。
- type は Conventional Commits 系。履歴で使われているのは次の 3 つ。必要なら標準の他の type も使ってよい。
  - `feat` — 機能・シーン・シェーダー等の追加（例: `feat: add StableFluids scene` / `feat: implement StableFluids`）
  - `refactor` — 挙動を変えない整理・ディレクトリ再編（例: `refactor: ディレクトリ構成の変更、細かい修正`）
  - `chore` — プロジェクト初期化・設定など（例: `chore: initialize Unity project`）
  - 他に必要なら `fix`（不具合修正）、`docs`、`perf`、`style`、`test`、`build`
- 件名は **英語でも日本語でもよい**。履歴では、新規追加は英語の動詞（`add` / `implement` / `initialize`）、リファクタは日本語、という傾向がある。迷ったら**直近のコミットの言語に合わせる**。
- 英語の場合は小文字始まりの命令形、末尾にピリオドを付けない。日本語の場合は体言止め（`〜の変更`）で、列挙は読点「、」でつなぐ。長さはおおむね 50 文字程度まで。
- 固有名（クラス名・シーン名・シェーダー名）は元の綴りのまま（`StableFluids`, `PingPongRenderTexture`）。

### 本文

- 件名の後に **空行を 1 つ**。
- 本文は **日本語**。技術用語・クラス名・カーネル名・アルゴリズム名は英語のまま混ぜる（`Semi-Lagrangian 移流`, `Jacobi 反復`, `AddVelocity カーネル`）。コード用のバッククォートは付けない。
- 変更点は `- ` の箇条書き。1 項目 1 変更で、文末は「〜を実装」「〜を作成」「〜をリファクタリング」「〜に対応」のように **体言止め／名詞+動作**。「です・ます」「した。」は使わない。
- 重要な変更には、2 スペースインデントの子箇条書きで **なぜそうしたか・どう効くか**（設計意図、アルゴリズムの狙い、副次的な効果）を添える。例:
  ```
  - コンピュートシェーダーで Stable Fluids（外力・移流・投影）を実装
    - Semi-Lagrangian 移流で、dt が大きくても破綻しない移流を実現
  ```
- 規模に応じて量を変える。
  - 小さな変更・追加 → 箇条書き 2〜4 行、子項目なし（`ba498a1`, `85928e2`）。
  - 機能実装 → 導入文 1 行 + 箇条書き + 子項目（`60b9450`）。
  - 追加物の列挙が主なら「〇〇クラスを実装」を並べる（`3fb5572`）。
- 導入文を付ける場合は、スコープを一文で言い切る（例: `StableFluidsの「外力による速度場の変化」と「染料の流れ」のみを実装`）。「のみ」「まで」などで**範囲の限定**を明示するのが好まれる。
- 件名の繰り返し（本文の先頭に件名と同じ行を入れる）は `60b9450` に見られる癖だが、**真似しない**。

## Unity プロジェクト特有の扱い

- `.meta` ファイルはアセット本体に付随するだけなので、本文では言及しない（アセット自体を記述する）。
- `.unity` シーンの差分は YAML の中身ではなく、「シーン構成の変更」「〇〇コンポーネントの配置・参照の更新」のように意味で要約する。シーンのみ変更されている場合も、それが何のための調整かを書く。
- 移動・リネーム（`git diff -M` で `{ => Scripts}/` など）は「ディレクトリ構成の変更」として 1 項目にまとめる。ファイルごとに列挙しない。
- 削除・追加が同じ意図の組（例: ファイルを消して別名で追加）なら、リネームとして 1 項目にする。
- `Packages/manifest.json` / `packages-lock.json` の変更は、追加・更新されたパッケージ名が分かるなら 1 項目で触れる。
- 画像・テクスチャ・動画などバイナリは、追加／差し替えの事実だけを書く。

## 注意

- 複数の無関係な変更が混ざっているときは、1 つのメッセージに無理にまとめず、「分けてコミットした方がよさそう」と伝え、分割案（どのファイルをどのコミットに入れるか）を添える。ただし求められたメッセージ自体は、まとめた版も出す。
- コミットに含めない方がよさそうなファイルは、メッセージとは別に一言指摘する。例: Unity の自動復旧ファイル（`Assets/_Recovery/`）、`Library/` 配下、一時ファイル、このスキル自身（`.claude/`）を意図せず含めていないか。判断はユーザーに任せ、勝手に除外しない。
- diff から読み取れない意図（なぜその変更をしたか）は推測で断定しない。確信が持てない箇所は本文を事実の記述（何を変えたか）にとどめ、必要ならユーザーに一言確認する。
- 出力は次の形式にする。

  ````
  ```
  <type>: <件名>

  - ...
  ```
  ````
  その後に 1〜2 行で「type をこう判断した理由」や分割の提案があれば添える。
